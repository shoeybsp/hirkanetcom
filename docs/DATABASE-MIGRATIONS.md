# Hirkanet database migrations

Hirkanet uses Flask-Migrate and Alembic as the only supported schema-management path.
The web application does not call `db.create_all()` and does not modify the schema during Gunicorn startup.

## Docker Compose startup

The application Compose project contains a one-shot `migrate` service:

```text
db becomes healthy
        ↓
migrate runs flask db upgrade
        ↓
migrate runs flask seed-defaults
        ↓
app starts Gunicorn
```

Normal startup remains:

```bash
docker compose up -d --build
```

Inspect migration output with:

```bash
docker compose logs migrate
```

A failed migration prevents the `app` service from starting. Correct the migration problem instead of bypassing this dependency.

## Existing installations

Revision `20260731_0001` is an adoption migration. It checks the existing schema and creates only missing baseline tables or indexes. This allows databases previously initialized by the old `db.create_all()` path to enter Alembic management without dropping their data.

Back up PostgreSQL before the first migration-managed deployment:

```bash
mkdir -p backups
docker compose exec -T db \
  pg_dump --username="$POSTGRES_USER" --format=custom --no-owner "$POSTGRES_DB" \
  > "backups/hirkanet-before-alembic-$(date +%F-%H%M%S).dump"
```

## Creating a schema change

After editing SQLAlchemy models, generate the revision from a local development virtual environment where the repository is writable:

```bash
source venv/bin/activate
flask --app api.app db migrate -m "describe the schema change"
```

The production `migrate` container is intentionally read-only and applies reviewed revisions only. Review the generated file under `migrations/versions/`; autogenerated migrations are drafts and must be reviewed before deployment.

Apply it with:

```bash
docker compose run --rm migrate flask --app api.app db upgrade
```

Commit both the model change and migration revision together.

## Current revision and history

```bash
docker compose run --rm migrate flask --app api.app db current
docker compose run --rm migrate flask --app api.app db history
```

## Rollback

Downgrades can be destructive. Take a verified backup first, review the revision's `downgrade()` function, and then run a specific downgrade deliberately:

```bash
docker compose run --rm migrate flask --app api.app db downgrade <revision>
```

Do not use migration downgrade as a substitute for restoring critical production data.

## Seeding

Default service records and the optional bootstrap administrator are managed separately from schema migration:

```bash
docker compose run --rm migrate flask --app api.app seed-defaults
```

The Compose migration service performs this command automatically after a successful upgrade. Seeding is idempotent.

## Foreign-key deletion policy

Revision `20260731_0002` encodes ownership in the database:

- Deleting a user deletes that user's subscriptions.
- Deleting a service deletes subscriptions for that service.
- Deleting a blog author preserves posts and sets `author_id` to `NULL`.
- Deleting a blog category preserves posts and sets `category_id` to `NULL`.

Revisions `20260802_0005` and `20260803_0006` add two more ownership rules:

- Deleting a user deletes that user's device assignments and API keys.
- Deleting a device deletes its client assignments. Collected snapshot
  files on disk under that device's `data_dir` are **not** removed by
  this cascade or by the admin panel's device-delete action - only the
  database rows.

**SQLite note:** SQLite does not enforce `ON DELETE CASCADE` by default.
`models.py` registers a `PRAGMA foreign_keys=ON` connect-event listener so
local/dev/test runs using the SQLite fallback actually get this same
cascade behavior; PostgreSQL enforces it natively regardless. This was
found and fixed after a device delete under SQLite left an orphaned
`DeviceAssignment` row that would not have occurred against PostgreSQL.

## Revision 20260731_0003: integrity constraints and indexes

This revision adds database-enforced role, status, service-type, subscription-date,
and subscription-uniqueness rules, plus composite indexes for common access and
blog queries. Before altering the schema it checks existing rows. If invalid or
duplicate data exists, the migration stops with a descriptive error and does not
silently modify production records. Correct the reported rows, take a fresh
backup, and rerun `flask --app api.app db upgrade`.

## Revision 20260801_0004: login rate limiting

Adds `login_rate_limits`, a database-backed counter table shared by every
application worker so failed-login tracking survives restarts and works
correctly across multiple Gunicorn processes (an in-memory counter would
not). See `docs/LOGIN-RATE-LIMITING-CHANGES.md` for the rate-limiting
design itself.

## Revision 20260802_0005: device inventory

Adds `devices` and `device_assignments`, replacing the single hardcoded
FortiGate configuration with an admin-managed inventory of any number of
devices, each independently collected and independently assigned to
client users. Device credentials are stored encrypted (`secret_crypto.py`),
never in plaintext.

This migration only creates the tables; it does not move any data. The
first time the application starts afterward, `models.py::_seed_defaults()`
registers the pre-existing flat `data/` directory as a `Device` row named
"Default FortiGate" so existing single-device installs keep working with
zero snapshot files moved. This seeding step, not the migration itself,
is what makes upgrading from a pre-multi-device install safe - the same
role revision `20260731_0001` plays for pre-Alembic installs.
