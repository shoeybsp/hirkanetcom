# Hirkanet Database Operations Guide

This document defines how Hirkanet creates, migrates, protects, monitors, logs, backs up, restores, and retains database data. PostgreSQL is the production database and the sole identity store.

## 1. Database role and stored data

PostgreSQL stores:

- Users and password hashes
- Roles
- Hirkanet services
- User-service subscriptions
- Blog categories
- Blog posts and metadata
- Alembic migration state

FortiGate policy data is not stored in the relational schema. It is stored as immutable, versioned snapshots inside the `hirkanet-app_hirkanet_data` named Docker volume, with an atomic active pointer. Uploaded media is also external to PostgreSQL.

The removed legacy `data/users.json` store must not be reintroduced. PostgreSQL is the only identity source.

## 2. Production topology and persistence

The database service is defined in `docker-compose.yml`:

```text
service: db
image: postgres:16-alpine
network: internal app-db bridge
host port: none
volume: postgres_data mounted at /var/lib/postgresql/data
```

The database is not published to the host or public network. The application reaches it through the internal Compose service name `db`.

The named volume persists through:

```bash
docker compose down
docker compose up -d
```

It is removed by destructive volume operations such as:

```bash
docker compose down -v
```

Never use `-v` in production unless permanent database deletion is explicitly intended and a verified recovery plan exists.

A persistent Docker volume is not a backup.

## 3. Required database configuration

Create `.env`:

```bash
cp .env.example .env
chmod 600 .env
```

Required non-secret settings:

```env
POSTGRES_DB=hirkanet
POSTGRES_USER=hirkanet
TZ=Europe/Riga
```

Create the password secret:

```bash
openssl rand -hex 32 > secrets/postgres_password
chmod 600 secrets/postgres_password
```

The password is mounted into containers at:

```text
/run/secrets/postgres_password
```

Hirkanet does not construct a plaintext `DATABASE_URL` in Compose. The application reads separate host, port, database, username, and secret-file values and builds the SQLAlchemy URL safely. Passwords containing URL-reserved characters therefore do not corrupt the connection string.

## 4. Database creation

PostgreSQL creates the configured database and initial database role only when the `postgres_data` volume is empty.

Start the stack:

```bash
docker compose up -d --build
```

Startup sequence:

```text
PostgreSQL health check
        ↓
Alembic migration service
        ↓
Idempotent default-data seeding
        ↓
Gunicorn application
```

The web application does not call `db.create_all()` and does not alter the schema at request-serving startup.

Check the services:

```bash
docker compose ps
docker compose logs --tail=200 db migrate app
```

## 5. Database health checks

The PostgreSQL container health check performs an authenticated SQL query:

```sql
SELECT 1;
```

The application readiness endpoint also checks database access:

```bash
curl --fail http://127.0.0.1:5000/readyz
```

The process-only liveness endpoint is:

```bash
curl --fail http://127.0.0.1:5000/livez
```

A failed readiness check can indicate:

- PostgreSQL is unavailable
- The password secret is incorrect
- The configured database or user is wrong
- Migrations failed
- The application cannot resolve or connect to `db`

## 6. Alembic and Flask-Migrate

Hirkanet uses Flask-Migrate/Alembic. Migration files are stored under:

```text
migrations/versions/
```

Apply all reviewed migrations:

```bash
docker compose run --rm migrate
```

The Compose migration service runs:

```bash
flask --app api.app db upgrade
flask --app api.app seed-defaults
```

View the current revision:

```bash
docker compose run --rm migrate \
  flask --app api.app db current
```

View migration history:

```bash
docker compose run --rm migrate \
  flask --app api.app db history
```

### Creating a migration during development

Use a writable local checkout and virtual environment:

```bash
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
flask --app api.app db migrate -m "describe the schema change"
```

Review the generated revision manually. Autogenerated migrations are drafts, not automatically trusted production changes.

Commit the model change and migration revision together.

### Migration rules

Before every production migration:

1. Create a PostgreSQL backup.
2. Complete a restore test.
3. Review `upgrade()` and `downgrade()`.
4. Check for table locks or long-running operations.
5. Schedule maintenance if the change is disruptive.
6. Apply the migration once through the one-shot migration service.
7. Confirm the current revision and application readiness.

Do not generate revisions inside the hardened read-only migration container.

## 7. Current integrity model

The database enforces key invariants rather than relying only on route validation.

### Foreign-key actions

- Deleting a user cascades to that user's subscriptions.
- Deleting a service cascades to subscriptions for that service.
- Deleting a blog author preserves blog posts and sets `author_id` to `NULL`.
- Deleting a blog category preserves blog posts and sets `category_id` to `NULL`.

### Check and uniqueness constraints

- User role must be `admin` or `client`.
- Blog status must be `draft` or `published`.
- Service type cannot be blank.
- Subscription end time must be later than start time when present.
- A user may have only one subscription row for a given service.

### Query indexes

The schema includes indexes for common service, subscription, and blog access paths, including:

```text
ix_services_type_active
ix_subscriptions_user_active
ix_subscriptions_service_active
ix_blog_posts_status_published_at
ix_blog_posts_category_status
```

Constraints are the final integrity authority. Route validators exist to provide friendly errors before a database constraint is reached.

## 8. Transactions and rollback handling

All application writes pass through the shared transaction boundary in:

```text
database_transactions.py
```

Expected behavior:

- Successful operations commit once.
- Integrity violations trigger rollback and a safe HTTP 409 response.
- Other database failures trigger rollback and a safe HTTP 500 response.
- SQL details are logged internally but are not exposed to users.
- A failed SQLAlchemy session is rolled back before it can be reused.
- Default seeding is atomic, preventing partial initialization.

Do not add direct `db.session.commit()` calls in routes. New write paths must use the centralized transaction helper.

## 9. Default data and bootstrap administrator

The idempotent seed command is:

```bash
docker compose run --rm migrate \
  flask --app api.app seed-defaults
```

It creates missing default records, including the configured bootstrap administrator and default service records.

Required inputs:

```env
BOOTSTRAP_ADMIN_USERNAME=admin
```

```text
secrets/bootstrap_admin_password
```

Seeding does not replace existing records blindly. Protect the bootstrap password and rotate administrative credentials according to policy.

## 10. Database logging

PostgreSQL container output is collected through Docker's `json-file` driver with rotation:

```text
max-size: 10m
max-file: 5
```

The optional Filebeat/Logstash stack identifies the database container through the Docker label:

```text
hirkanet_log_role=database
```

Application database failures are emitted as structured JSON by Hirkanet. Logs include request identifiers and safe error classification, but secrets and sensitive keys are redacted.

The current PostgreSQL configuration relies mainly on container output. For stronger production auditing, deliberately configure PostgreSQL parameters such as connection, disconnection, checkpoint, lock-wait, and slow-statement logging. Do not enable indiscriminate full statement logging in production because SQL can contain sensitive data and generate excessive volume.

Recommended production review items:

```text
log_connections
log_disconnections
log_checkpoints
log_lock_waits
deadlock_timeout
log_min_duration_statement
```

Any PostgreSQL logging change should be load-tested and documented in the deployment configuration.

## 11. Backup policy

Run:

```bash
./scripts/postgres-backup.sh
```

The backup workflow:

1. Runs `pg_dump` inside the database container.
2. Reads the password only from the mounted secret.
3. Creates a PostgreSQL custom-format dump.
4. Creates a SHA-256 checksum.
5. Creates metadata.
6. Validates the archive with `pg_restore --list`.
7. Restores it into a disposable database by default.
8. Confirms expected Hirkanet tables and `alembic_version` exist.
9. Marks the backup `restore_test=passed` only after successful validation.

Backup set:

```text
backups/postgres/<timestamp>.dump
backups/postgres/<timestamp>.dump.sha256
backups/postgres/<timestamp>.dump.meta
```

A backup is not operationally valid merely because `pg_dump` succeeded. It should be considered valid only after the restore test passes.

Default retention:

- Remove backup sets older than 14 days when policy permits
- Always keep at least the seven newest backup sets

Override for one run:

```bash
RETENTION_DAYS=30 KEEP_MINIMUM=14 \
  ./scripts/postgres-backup.sh
```

Copy successful backup sets to encrypted off-host storage. The local backup directory is on the same failure domain as the application host.

## 12. Restore testing

Test a backup independently:

```bash
./scripts/postgres-restore-test.sh \
  backups/postgres/<backup>.dump
```

The procedure checks:

- Checksum integrity
- Valid PostgreSQL archive structure
- Full restore into a disposable database
- Expected application tables
- Alembic revision state
- Cleanup of the test database after success or failure

Schedule periodic recovery drills on another host, not only on the production server.

## 13. Database recovery

The safe default is restoring into a separate database:

```bash
./scripts/postgres-restore.sh \
  --backup backups/postgres/<backup>.dump \
  --target-db hirkanet_recovery \
  --confirm-restore
```

Inspect the recovered data before cutover.

Restoring over the configured production database is blocked unless explicitly allowed:

```bash
./scripts/postgres-restore.sh \
  --backup backups/postgres/<backup>.dump \
  --target-db "$POSTGRES_DB" \
  --confirm-restore \
  --allow-production-target
```

Production replacement procedure:

1. Announce maintenance.
2. Stop or block application writes.
3. Back up the current production database.
4. Verify the selected recovery dump.
5. Restore deliberately.
6. Run migrations.
7. Start the app.
8. Verify `/readyz`, login, subscriptions, blog records, and representative administration actions.

Read `POSTGRES-BACKUP-RESTORE.md` before performing recovery.

## 14. Storage monitoring

Run the read-only monitor:

```bash
./scripts/storage-monitor.py
```

JSON output:

```bash
./scripts/storage-monitor.py --json
```

Database-related checks include:

- PostgreSQL database size
- PostgreSQL Docker-volume filesystem use
- Backup directory size
- Age of the newest restore-tested backup
- Host filesystem utilization

Exit codes:

```text
0 healthy
1 warning or unavailable dependency
2 critical
```

Default database thresholds:

| Metric | Warning | Critical |
|---|---:|---:|
| PostgreSQL volume | 80% | 90% |
| PostgreSQL database | 5 GiB | 10 GiB |
| Latest verified backup age | 26 hours | 48 hours |
| Backup directory | 20 GiB | 40 GiB |

Configure them in `.env`:

```env
POSTGRES_VOLUME_WARN_PERCENT=80
POSTGRES_VOLUME_CRITICAL_PERCENT=90
POSTGRES_DB_WARN_BYTES=5368709120
POSTGRES_DB_CRITICAL_BYTES=10737418240
BACKUP_MAX_AGE_HOURS=26
BACKUP_CRITICAL_AGE_HOURS=48
BACKUP_STORAGE_WARN_BYTES=21474836480
BACKUP_STORAGE_CRITICAL_BYTES=42949672960
```

Route non-zero monitoring results to an external alerting system. Local logs alone are insufficient.

## 15. Retention management

Preview retention actions:

```bash
./scripts/storage-retention.py
```

Apply reviewed actions:

```bash
./scripts/storage-retention.py --apply
```

For PostgreSQL, retention manages:

- Expired complete backup sets
- Abandoned partial or temporary backup files
- The configured minimum number of newest backups

Relevant settings:

```env
RETENTION_DAYS=14
KEEP_MINIMUM=7
BACKUP_PARTIAL_MAX_AGE_HOURS=24
```

Retention does not replace off-host backups, restore testing, or recovery drills.

## 16. Capacity and performance inspection

Database size:

```bash
docker compose exec -T db sh -ec '
  export PGPASSWORD="$(cat /run/secrets/postgres_password)"
  psql --username="$POSTGRES_USER" --dbname="$POSTGRES_DB" \
    --no-password --command="SELECT pg_size_pretty(pg_database_size(current_database()));"
'
```

Largest user tables:

```sql
SELECT
    schemaname,
    relname,
    pg_size_pretty(pg_total_relation_size(relid)) AS total_size
FROM pg_catalog.pg_statio_user_tables
ORDER BY pg_total_relation_size(relid) DESC;
```

Useful operational checks also include:

- Active and idle connections
- Long-running transactions
- Blocking queries and locks
- Deadlocks
- Index usage
- Table and index bloat
- Autovacuum activity
- Replication or backup lag when those features are introduced

PostgreSQL should be monitored before limits are reached, not only after application failures begin.

## 17. Database user and privilege management

The PostgreSQL bootstrap role created through `POSTGRES_USER` may have broad privileges. For a mature production deployment, use separate roles for:

- Application runtime
- Schema migrations
- Read-only reporting or monitoring
- Backup operations where practical

Apply least privilege and rotate credentials under a documented process. Avoid exposing PostgreSQL outside the internal Docker network.

## 18. Local SQLite development

When production PostgreSQL variables are not configured, local development may use SQLite under `instance/`.

Initialize it through migrations:

```bash
python3 -m flask --app api.app db upgrade
python3 -m flask --app api.app seed-defaults
```

If the application reports:

```text
sqlite3.OperationalError: no such table: blog_posts
```

then the local schema has not been migrated.

SQLite is a development convenience, not the production database. PostgreSQL-specific behavior, concurrency, constraints, and migrations must still be tested against PostgreSQL before release.

## 19. Scheduling recommendations

Example daily verified backup:

```cron
15 2 * * * cd /srv/hirkanet && ./scripts/postgres-backup.sh >> /var/log/hirkanet-postgres-backup.log 2>&1
```

Example daily storage monitor:

```cron
30 2 * * * cd /srv/hirkanet && ./scripts/storage-monitor.py --json >> /var/log/hirkanet-storage.jsonl 2>&1
```

Example weekly reviewed retention apply:

```cron
45 2 * * 0 cd /srv/hirkanet && ./scripts/storage-retention.py --apply >> /var/log/hirkanet-retention.log 2>&1
```

Use a dedicated service account. Docker-group membership is effectively privileged and must be tightly controlled.

## 20. Database operational checklist

### Daily

- [ ] Verify the newest backup reports `restore_test=passed`.
- [ ] Check storage-monitor exit status.
- [ ] Review database and application error logs.
- [ ] Investigate failed migrations or readiness checks.

### Weekly

- [ ] Confirm off-host backup replication.
- [ ] Review database and volume growth.
- [ ] Review slow queries, lock waits, and connection use.
- [ ] Preview and apply retention under change control.

### Monthly

- [ ] Perform a recovery drill on a separate database or host.
- [ ] Review database roles and access.
- [ ] Review migration history against deployed application code.
- [ ] Review retention thresholds and capacity forecasts.
- [ ] Confirm secret and administrator credential rotation policy.

### Before every release

- [ ] Take and restore-test a backup.
- [ ] Review every Alembic revision.
- [ ] Test upgrades against PostgreSQL.
- [ ] Verify constraints and indexes after migration.
- [ ] Confirm the application transaction helper covers new write paths.
- [ ] Verify `/readyz` after deployment.

## 21. Prohibited operations without an explicit recovery plan

Do not perform these casually in production:

```bash
docker compose down -v
docker volume rm hirkanet-app_postgres_data
rm -rf backups/postgres
flask --app api.app db downgrade
```

Do not:

- Edit migration history after it has been deployed.
- Delete or modify the `alembic_version` row manually.
- Use `db.create_all()` as a production migration mechanism.
- Reintroduce file-backed user identity storage.
- Restore unverified dumps over production.
- Store PostgreSQL passwords in `.env`, source code, logs, or command history.
